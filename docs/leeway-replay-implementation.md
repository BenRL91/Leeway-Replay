# Leeway Replay implementation

Routes: `/` is the Leeway Replay general library. `/replay` is the configured coach workspace. `/replay?review=<UUID>` edits a review. `/replay/preview/<UUID>` reads the owner's saved draft through an owner-only API. `/replay/view/<UUID>` contains the player-only shell; content and media require released-review authorization. No draft/edit/admin payload is returned to a player.

R2 `replay/reviews/<UUID>.json` holds schema-local review objects with owner, draft, release snapshot, draft/released viewer grants, revision and state. Conditional writes prevent stale saves. Existing `users/<identity>/library.json` and uploaded object keys are unchanged. There is no destructive migration. Canonical review IDs are generated server-side. Verified LeewayPB identity now authorizes data actors; private Sites identity remains the audience gate and authorizes the original owner’s explicit library-link confirmation. Coach ID is the existing verified Site owner in `app/server/replay.mjs`; changing it is a deliberate app-role change.

The reviewer can import matching general Leeway Replay notes as independent categorized feedback. General notes/tutorials remain untouched. Source selection reuses its existing account-scoped file list/upload endpoints. Shared `Leeway ReplayPlayback` supplies YouTube API loading and seek bounds to the general app, plus Replay's stable video component. Native uploaded video is streamed using the existing R2 byte-range semantics. Replay media goes through a review-scoped authorization boundary rather than exposing the owner's file route.

Save-and-release validates all required fields and intended viewer, and writes draft plus released snapshot atomically. A malformed or incomplete release saves nothing. Normal draft saves can remain incomplete. Revocation blocks new review/media requests; downloaded copies cannot be recalled. A viewer polls every 15 seconds and checks when returning to the tab. Editing a released review never modifies the player-visible snapshot or its grants until release.

No Coaching, PaddleLog, Pickle Point, shared auth or payment code was accessed or modified. External customer delivery remains subject to explicit private admission and identity mapping. Proposed handoff: `leeway-replay-handoff.md`.

Email sharing adds optional draftViewerEmails/viewerEmails arrays with at most one intended recipient across email and ID grants. Existing ID grants and data are preserved. The principal passed to review authorization is obtained from server-side Supabase getUser, never request-supplied email. Email confirmation is required. Email/ID changes remain draft-only until release; revocation clears both. Discussion audiences retain the original recipient boundary when grants change. `/api/replay/mine` returns only authorized released reviews, using their released title and player name; drafts and revoked reviews are absent. `/replay` shows this student list for non-coach accounts. The coach editor offers Recipient email, Use student test account, Release review, Copy private review link and Revoke access.

To test: as coach, choose a review, set the recipient test email and Release review. In a separate/private browser session, accept private Site admission using the test email and sign into LeewayPB with the same verified email. Visit `/replay` to open the released review and post a timestamped question. No existing reviews were automatically shared with the tester. Personal notes/tutorial sharing is not included in this coaching-review sharing slice.

### Feedback persistence and flexible plans

Add feedback and Update feedback save the complete current review draft through the existing revision-checked draft API. The composer clears only after server confirmation; failures retain the original feedback text and show an unsaved error. Saves never release the review. Priority/drill editors now use add/remove lists instead of fixed slots. New drafts start with empty lists; existing nonempty content is preserved. Release requires at least one completed priority and one completed drill; each list accepts up to 50 items within existing request-size limits. Player headings reflect variable lists. Verified through browser-UI-to-Worker tests, including Decision-making feedback, failed-save retry, double-click suppression, reload, update without duplication, and variable plan release validation.
